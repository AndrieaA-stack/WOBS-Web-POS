Normalization Pipeline

Database Normalization: UNF → 1NF → 2NF → 3NF

A complete, mathematically sound decomposition of Laura's Store Point-of-Sale & Online Delivery management system. Follow the systematic transition from unnormalized transaction receipts into a clean, 3NF-compliant relational database schema with full referential integrity.

Production Target: 5 Normalized Tables • 0 Redundancy • 100% 3NF
UNF • Stage 0

Unnormalized Form (UNF) — Flat Sales Receipt Document

Status: Contains Repeating Groups & Non-Atomic Attributes
UNF Definition & Problem: A single flat receipt/ledger document where customer information, delivery addresses, and multiple purchased items are stuffed into a single record. It violates atomicity and exhibits repeating groups (`Items [ ... ]`).

Functional Schema Notation (UNF):

FLAT_SALES_RECORD (
  ReceiptNo, TransactionDate, CashierName, CashierUsername,
  CustomerName, CustomerAddress, CustomerPhone,
  { ProductID, Barcode, ProductName, Category, UnitCost, UnitPrice, Quantity, Subtotal } ← REPEATING GROUP,
  GrandTotal, PaymentMethod, GCashReference, PaymentProofScreenshot, OrderStatus
)

Sample Raw Ledger Table in UNF:

ReceiptNo CustomerName CustomerAddress CustomerPhone Items Purchased (Repeating Group) GrandTotal PaymentMethod Status
WOBS-100201 Juan Dela Cruz Blk 4 Lot 12 Sampaguita St, Pandayan, Meycauayan 09171234567 [P-001] Bear Brand Adult Plus (x2 @ ₱35.00)
[P-004] San Miguel Pale Pilsen (x3 @ ₱55.00) 		₱235.00 GCash Completed
WOBS-100202 Maria Santos 124 MacArthur Highway, Saluysoy, Meycauayan 09189876543 [P-002] Lucky Me Pancit Canton (x5 @ ₱18.00) ₱90.00 Cash Completed
Identified Violations in UNF:
  • Repeating Groups: Multiple items exist within a single transaction record, requiring dynamic arrays or comma-delimited values.
  • Non-Atomic Fields: CustomerAddress contains Street, Barangay, and City combined in one string.
  • No Single Primary Key: Standard SQL engines cannot enforce unique integrity across nested lists.
1NF • Stage 1

First Normal Form (1NF) — Elimination of Repeating Groups & Atomicity

Rule: Atomic Values • Unique Rows • Composite Primary Key
Transformations Applied to Achieve 1NF:
  1. Flattening Repeating Groups: Every product in an order is split into its own distinct, atomic row.
  2. Atomicity of Attributes: CustomerAddress is decomposed into atomic units: Street, Barangay, and City.
  3. Identification of Primary Key: Composite Primary Key is established as: (TransactionID, ProductID).

Functional Schema Notation (1NF):

TRANSACTION_SALES_1NF (
  TransactionID, ProductID, Barcode, ProductName, Category, Cost, Price, Quantity,
  CustomerID, CustomerFullname, CustomerUsername, CustomerPhone, Street, Barangay, City,
  Total, PaymentMethod, GCashRef, PaymentProof, Status, DateCreated
)

Flattened 1NF Table Sample:

TransactionID ProductID ProductName Price Qty CustomerFullname Street Barangay City
WOBS-100201 P-001 Bear Brand Adult Plus ₱35.00 2 Juan Dela Cruz Blk 4 Lot 12 Sampaguita St Pandayan Meycauayan
WOBS-100201 P-004 San Miguel Pale Pilsen ₱55.00 3 Juan Dela Cruz Blk 4 Lot 12 Sampaguita St Pandayan Meycauayan

Functional Dependencies in 1NF:
(TransactionID, ProductID) → Quantity, Subtotal Full Dependency
ProductID → Barcode, ProductName, Category, Cost, Price Partial Dependency (Depends only on ProductID!)
TransactionID → CustomerID, CustomerFullname, Phone, Street, Total, Status Partial Dependency (Depends only on TransactionID!)
Why 1NF is Insufficient (Partial Dependencies): Attributes like ProductName, Category, and Price depend ONLY on ProductID, NOT on the entire composite key (TransactionID, ProductID). This causes massive redundancy and violates 2NF.
2NF • Stage 2

Second Normal Form (2NF) — Elimination of Partial Dependencies

Rule: 1NF Satisfied • No Non-Key Attribute Depends on Part of a Composite Key
Transformations Applied to Achieve 2NF: Decompose the table into separate entities based on their independent functional determinants:
  • Extract PRODUCTS into its own table with ProductID as Primary Key.
  • Maintain TRANSACTIONS with TransactionID as Primary Key and ProductID as Foreign Key.

Decomposed Schemas in 2NF:

PRODUCTS (2NF) (
  ProductID, Barcode, Name, Category, Cost, Price, Stock, Expiry, Image, DateAdded
)

TRANSACTIONS (2NF) (
  TransactionID, ProductID, CustomerID, CustomerFullname, CustomerUsername, CustomerPhone,
  Street, Barangay, City, Total, PaymentMethod, GCashRef, PaymentProof, Status, DateCreated
)
Functional Dependencies in 2NF:
In PRODUCTS: ProductID → Barcode, Name, Category, Cost, Price, Stock, Expiry Fully Dependent on PK
In TRANSACTIONS: TransactionID → ProductID, CustomerID, Total, Status, DateCreated Fully Dependent on PK
In TRANSACTIONS: CustomerID → CustomerFullname, CustomerUsername, Phone, Street, Barangay, City Transitive Dependency! (Non-Key → Non-Key)
Why 2NF is Insufficient (Transitive Dependencies): In the TRANSACTIONS table, TransactionID → CustomerID, and CustomerID → CustomerFullname, Phone, Street. The customer demographic details depend on CustomerID (a non-key attribute in transactions), not directly on the primary key TransactionID. This is a Transitive Dependency!
3NF • Stage 3 (Final Target)

Third Normal Form (3NF) — Elimination of Transitive Dependencies

Production Active Schema
Codd's Golden Rule Satisfied: "Every non-key attribute must provide a fact about the key, the whole key, and nothing but the key, so help me Codd." All transitive dependencies are eliminated by decoupling CUSTOMERS and ADMIN_ACCOUNTS into distinct relational tables.

Audit

Anomaly Resolution Analysis — Before vs After Normalization

Validation: Insertion, Update, and Deletion Safeguards
Insertion Anomaly
In UNF & 1NF: You could not add a brand new product to the store inventory without also inventing a fake dummy transaction, because TransactionID was part of the primary key.
Resolved in 3NF: Products are entered directly into products with their own primary key ProductID regardless of sales history.
Update Anomaly
In UNF & 1NF: If a customer changed their phone number or a product's supplier cost increased, hundreds of historical sales records had to be searched and updated individually.
Resolved in 3NF: Updating customer credentials or product prices requires modifying exactly 1 single row in customers or products.
Deletion Anomaly
In UNF & 1NF: If a cashier cancelled or deleted an erroneous transaction, the only recorded data for that customer or that specific product item would be accidentally destroyed.
Resolved in 3NF: Deleting a record from transactions leaves the customer profile and product catalog completely intact.

Production PostgreSQL Schema (schema.sql)

PostgreSQL 14+ Dialect • Quoted Primary Identifiers 
-- ========================================================
-- 3NF NORMALIZED RELATIONAL DATABASE SCHEMA (WOBS POS)
-- ========================================================

-- 1. PRODUCTS TABLE
CREATE TABLE IF NOT EXISTS products (
    "ProductID" VARCHAR(100) PRIMARY KEY,
    barcode VARCHAR(100) UNIQUE,
    name VARCHAR(255) NOT NULL,
    category VARCHAR(100) NOT NULL,
    cost NUMERIC(10, 2) DEFAULT 0.00,
    price NUMERIC(10, 2) NOT NULL DEFAULT 0.00,
    stock INTEGER NOT NULL DEFAULT 0,
    expiry DATE,
    image TEXT
);

-- 2. CUSTOMERS TABLE
CREATE TABLE IF NOT EXISTS customers (
    "CustomerID" VARCHAR(100) PRIMARY KEY,
    fullname VARCHAR(255) NOT NULL,
    username VARCHAR(100) UNIQUE NOT NULL,
    password VARCHAR(255) NOT NULL,
    phone VARCHAR(50),
    city VARCHAR(100),
    barangay VARCHAR(100),
    street TEXT,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

-- 3. TRANSACTIONS TABLE (With Foreign Key to products and customers)
CREATE TABLE IF NOT EXISTS transactions (
    "TransactionID" VARCHAR(100) PRIMARY KEY,
    "ProductID" VARCHAR(100) REFERENCES products("ProductID"),
    customer_id VARCHAR(100),
    customer_username VARCHAR(100),
    customer_name VARCHAR(255) NOT NULL DEFAULT 'Guest Customer',
    address TEXT NOT NULL,
    gcash_ref VARCHAR(255) DEFAULT 'SCREENSHOT_ATTACHED',
    payment_proof TEXT,
    total NUMERIC(10, 2) NOT NULL DEFAULT 0.00,
    status VARCHAR(50) NOT NULL DEFAULT 'Pending',
    payment_method VARCHAR(50) DEFAULT 'GCash',
    date_created TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

-- 4. ADMIN ACCOUNTS TABLE
CREATE TABLE IF NOT EXISTS admin_accounts (
    "AdminID" SERIAL PRIMARY KEY,
    fullname VARCHAR(255) NOT NULL,
    username VARCHAR(100) UNIQUE NOT NULL,
    password VARCHAR(255) NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

-- 5. PENDING ADMIN ACCOUNTS TABLE
CREATE TABLE IF NOT EXISTS pending_admin_accounts (
    "PendingAdminID" SERIAL PRIMARY KEY,
    fullname VARCHAR(255) NOT NULL,
    username VARCHAR(100) UNIQUE NOT NULL,
    password VARCHAR(255) NOT NULL,
    requested_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

-- PERFORMANCE INDEXES
CREATE INDEX IF NOT EXISTS idx_products_barcode ON products(barcode);
CREATE INDEX IF NOT EXISTS idx_transactions_productid ON transactions("ProductID");
CREATE INDEX IF NOT EXISTS idx_transactions_status ON transactions(status);
CREATE INDEX IF NOT EXISTS idx_transactions_date ON transactions(date_created DESC);
CREATE INDEX IF NOT EXISTS idx_customers_username ON customers(LOWER(username));
CREATE INDEX IF NOT EXISTS idx_transactions_customer_username ON transactions(customer_username);
